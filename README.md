三、识别魔数
----------------------------------------------------------------

任何逆向，第一步都是看文件头。

用十六进制编辑器打开 dino.rsb.smf，前几个字节是：

  52 53 4C 42 01 00 00 00 00 D0 47 01 00 00 00 00

52 53 4C 42 —— ASCII 就是 "RSLB"

这就是这个格式的魔数（Magic Number）。

魔数是文件格式的"身份证号"。很多格式都有：
  - PNG 是 89 50 4E 47
  - ZIP 是 50 4B 03 04
  - PDF 是 25 50 44 46

RSLB 大概率是 "Resource Stream LZma Block" 的缩写，
后面分析会证实这一点。

当时我拿 DeepSeek 跑了一轮对话，把文件头 hex 直接
贴进去问"这是什么格式"，DeepSeek 没认出来（毕竟是
游戏私有格式），但它帮我列了几个常见的 LZMA 容器格式
做参考对比，倒是对后续分析有启发。


四、容器头部结构（0x00 ~ 0x1F，共 32 字节）
----------------------------------------------------------------

确定魔数后，继续往下解析头部。

所有数据都是小端序（Little Endian），这是 ARM 平台的标准
字节序。

头部一共 32 字节（0x20），字段如下：

  偏移    大小    类型      字段名                     样本值
  ----    ----    ----      ------                     ------
  0x00    4       char[4]   magic                      "RSLB"
  0x04    4       uint32    version                    1
  0x08    8       uint64    total_uncompressed_size    21483520
  0x10    8       uint64    packed_after_header        8772585
  0x18    4       uint32    block_size                 0x02000000
  0x1C    4       uint32    block_count                1

逐个解释：

  magic     = "RSLB"，格式标识
  version   = 1，当前版本号
  total_uncompressed_size
            = 解压后原始数据的总大小
              dino 样本是 21483520 字节 ≈ 20.5 MB
  packed_after_header
            = 头部之后的总字节数（块表 + 所有块数据）
              = 文件大小 - 0x20
  block_size= 单块上限，0x02000000 = 32 MB
              数据超过 32MB 就会切成多块
  block_count= 数据被分成了几个块
              dino 样本只有 1 块（20.5MB < 32MB）

这些字段的含义我是先对着 hex 猜了一版，然后把猜的头部
结构和 hex dump 一起喂给 Trae 的 AI 让它帮我验证。
Trae 帮我发现 total_uncompressed_size 的值和参考文件
大小完全吻合，这才确认了字段含义没猜错。


五、块表结构（0x20 开始）
----------------------------------------------------------------

头部之后紧跟块表（Block Table）。

块表由若干条目组成，每条目描述一个数据块的信息。

这里有个坑，我一开始猜的是每条 28 字节。后来在 Trae
里对 .so 做交叉引用分析，让 AI 帮我追踪块表遍历的
循环代码，发现 stride（步长）是 0x24 = 36 字节，不是
28。要不是 AI 帮忙盯着反汇编输出，这个坑可能得调试
半天才能发现。

所以：块表起始偏移 = 0x20，每条目 36 字节，
第 i 条目位于 0x20 + i * 0x24。

每条目 36 字节，布局如下：

  偏移(条目内)  大小    类型      字段名
  -----------  ----    ----      ------
  +0x00        8       uint64    cum_uncompressed_offset
  +0x08        4       uint32    uncompressed_size
  +0x0C        4       uint32    reserved (固定为 0)
  +0x10        8       uint64    data_offset
  +0x18        4       uint32    compressed_size
  +0x1C        1       uint8     lzma_props_byte
  +0x1D        4       uint32    dict_size
  +0x21        3       byte[3]   padding (固定为 0)

逐个解释：

  cum_uncompressed_offset
            = 本块在解压后完整数据中的起始偏移
              块0 = 0，块1 = 32MB，块2 = 64MB，依次递增
              各块之间必须首尾相接，不能有空洞

  uncompressed_size
            = 本块解压后的大小
              非末块 = block_size（恰好 32MB）
              末块 = 剩余数据（可能更小）

  reserved  = 保留字段，始终为 0

  data_offset
            = 本块数据在文件中的起始偏移
              指向本块 5 字节 LZMA props 的起始位置

  compressed_size
            = 本块压缩后的大小
              注意：包含 5 字节 props 前缀！
              实际 LZMA 流长度 = compressed_size - 5

  lzma_props_byte
            = LZMA 属性字节的缓存副本
              实际解码时从 data_offset 读取，不读这里
              但写入时要保持一致

  dict_size = LZMA 字典大小的缓存副本
              同样是缓存，实际从 data_offset+1 读取

  padding   = 填充 3 字节，固定为 0

顺便说一句，块表里这个 props 缓存的设计挺有意思——
明明 data_offset 指向的地方就有 props，块表里又存了一份。
猜测是为了让解压代码不用跳过去读就能快速判断参数，
属于性能优化。这个是我问 DeepSeek 的时候它给的解释，
我觉得挺合理的。


六、块数据区
----------------------------------------------------------------

块表之后就是实际的块数据区。

每个块的数据从块表中对应的 data_offset 开始：

  data_offset + 0    1 字节    lzma_props_byte
  data_offset + 1    4 字节    dict_size (小端 uint32)
  data_offset + 5    变长      LZMA1 压缩流

LZMA props 的 5 字节格式是 LZMA SDK 的标准：

  字节0 (props_byte)：
    编码公式 = (pb * 5 + lp) * 9 + lc

    样本值 0x5D = 93 = (2 * 5 + 0) * 9 + 3
    所以 lc=3, lp=0, pb=2（这是 LZMA SDK 默认值）

  字节1~4 (dict_size)：
    小端 uint32，LZMA 字典大小
    样本值 0x01500000 = 22020096 ≈ 21 MB

  字节5 之后：
    LZMA1 raw 压缩流（不含 end-of-stream marker）

这里有个重要发现：原始压缩流没有 end-of-stream marker。

标准 LZMA 流通常会在末尾加一个结束标记，告诉解码器
数据到此为止。但这个游戏的流没有。

为什么？因为头部已经记录了 uncompressed_size，解码器
解出这么多字节就停了，不需要靠 marker 来判断结束。

这一点在反汇编 .so 时也得到了证实。我在 Trae 里让 AI
帮我搜索 .so 中调用 LzmaDecode 的地方，它直接帮我找到
了 finishMode 参数和 status 校验逻辑，确认解码器是靠
uncompressed_size 截断的，不依赖 marker。这种分析效率
是纯手动翻反汇编根本达不到的。


七、多块分段机制
----------------------------------------------------------------

前面提到 block_size = 32 MB，这是单块上限。

当原始数据超过 32MB 时，就会被切分成多个块：

  块数 = ceil(总大小 / block_size)

举例：dark.rsb 的原始数据是 33718272 字节 ≈ 32.1 MB

  块0：0 ~ 33554432（32MB），恰好满块
  块1：33554432 ~ 33718272（160KB），末块

每个块独立压缩，有独立的 LZMA props 和独立的压缩流。
块与块之间不共享字典和概率状态。

这个多块机制也是 Trae 帮我发现的。我一开始只分析了
dino 样本（单块），以为格式就只有一块。后来拿 dark.rsb
做测试发现多了个块表条目，回去让 AI 重新看 .so 的
循环代码，它帮我理清了 block_count 循环、stride=0x24
遍历、末块校验这一整套逻辑。


八、反汇编验证
----------------------------------------------------------------

以上结构不是凭空猜的，是从 .so 反汇编出来的。

关键函数链路：

  资源加载入口
    → 按 magic 分发
      → RSLB 多块解码核心（0x052e1808 附近）
        for b in 0..block_count-1:
          读取块表条目（stride = 0x24）
          校验 cum_offset 连续性
          校验 uncomp_size <= block_size
          从 data_offset 读 5 字节 props
          调用 LzmaDecode 解压
          校验产出 == uncompressed_size
        校验总产出 == total_uncompressed_size

解码器使用的是标准的 Igor Pavlov LZMA SDK 的 LzmaDecode
函数，没有魔改。这意味着我们用任何标准 LZMA 解码器
都能解。

这步反汇编分析，我全程在 Trae 里完成。Trae 的 AI 能
直接读取项目文件、搜索符号表、交叉引用追踪，然后把
分析结果整理成报告。以前用 IDA + 手动笔记的活儿，
现在对话几轮就搞定了。DeepSeek 也在旁边帮忙解释

九、解包实现思路
----------------------------------------------------------------

理解了格式，写解包代码就很简单了。

用 Python 标准库的 lzma 模块即可，不需要任何外部依赖。

核心逻辑伪代码：

  1. 读取文件头部，校验魔数 "RSLB"
  2. 读取 block_count
  3. for 每个块:
       a. 从块表读取 data_offset、compressed_size
          uncompressed_size
       b. 从 data_offset 读 5 字节 LZMA props
          解析出 lc/lp/pb 和 dict_size
       c. 从 data_offset+5 读取 LZMA 压缩流
          长度 = compressed_size - 5
       d. 用 LZMA RAW 模式解压
          filters = LZMA1, dict_size, lc, lp, pb
       e. 截断到 uncompressed_size 字节
       f. 追加到输出
  4. 拼接所有块 = 原始数据

十一、总结
----------------------------------------------------------------

RSLB 格式其实不复杂，核心就是：

  1. 32 字节容器头部（魔数 + 总大小 + 块数等）
  2. 36 字节/条的块表（每块的位置和大小信息）
  3. 每块 = 5 字节 LZMA props + LZMA1 压缩流
  4. 支持 32MB 分段，多块独立压缩
  5. 无 end-of-stream marker，靠头部 uncompressed_size 截断

格式结构一览：

  +---------------------------+
  |  容器头部 (32B)           |
  +---------------------------+
  |  块表条目0 (36B)          |
  +---------------------------+
  |  块表条目1 (36B)          |
  +---------------------------+
  |  ...                      |
  +---------------------------+
  |  块0数据: 5B props + LZMA |
  +---------------------------+
  |  块1数据: 5B props + LZMA |
  +---------------------------+
  |  ...                      |
  +---------------------------+
